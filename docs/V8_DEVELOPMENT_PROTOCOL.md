# V8 Candidate-Level Multimodal Reranker: Development Protocol

## 1. Status and scope

This protocol defines a new V8 development study after the V7 technical
freeze. V7 configuration, cohorts, results, and claims must not be modified.
The V8 confirmation case IDs are not generated by this protocol commit.

V8 tests whether a candidate-level learned multimodal reranker can improve
closed-set paired-report retrieval over a validation-selected global
text/image fusion weight on a new case-ID-disjoint confirmation cohort.

The study remains same-source OpenI/IU-Xray evaluation. It is not external
validation, patient-level validation, image diagnosis, or clinical utility
evaluation.

## 2. Development and confirmation separation

V8 development reuses the tracked V7 development manifest only as development
data:

```text
Train A       240 cases / 360 questions
Train B       240 cases / 360 questions
Validation    240 cases / 360 questions
```

The V8 confirmation frame is formed after excluding all V7 development cases
and all V7 confirmation cases from the post-prior-use eligible source frame.
The final V8 confirmation IDs are generated only after this protocol, the
development decision record, and the V8 confirmation protocol are committed.

No V8 confirmation outcome may be used for model selection, feature selection,
loss selection, threshold selection, prompt selection, or qualitative tuning.

## 3. Frozen data policy

The source is `data/processed/openi_cases.jsonl`. Case IDs are canonicalized as
`str(value).strip()`. Report-indexed strata are defined by the processed
`problems` field:

```text
normal       -> normalized problems == "normal"
abnormal     -> non-empty label excluding "normal" and "no indexing"
indeterminate -> normalized problems == "no indexing"
```

Only normal and abnormal cases enter the primary stratification frame. The
source case, prior-use manifest, development manifest, selection frame, and
final cohort all receive SHA-256 fingerprints based on sorted unique case IDs
joined by LF UTF-8 with no trailing LF.

## 4. Frozen confirmation cohort design

The confirmation cohort-generation design is:

```text
selection seed       = 8026
selection domain     = v8-selection
assignment domain    = v8-assignment
selected normal      = 170
selected abnormal    = 70
target normal        = 85
target abnormal      = 35
distractor normal    = 85
distractor abnormal  = 35
```

Selection is performed separately within normal and abnormal strata by
ascending SHA-256 order of:

```text
<selection domain>|<seed>|<canonical case ID>
```

Target/distractor assignment uses a separate domain-separated SHA-256 order
within each selected stratum. No outcome-driven replacement is allowed after
the cohort manifest is generated. A data-integrity failure must be recorded as
a protocol deviation; it must not be silently replaced.

## 5. Frozen retrieval inputs

Each query is formed from the clinical indication and question. BM25 creates a
Top-100 candidate shortlist. MedSigLIP image/report similarity is computed with
the existing V6 sentence-aware, at-most-64-token chunking policy and frozen
image-view aggregation. Text and image scores are independently min-max
normalized within the shortlist. Ties are resolved by descending score and
ascending canonical case ID.

The candidate-level reranker is not allowed to inspect pixels directly. It
receives precomputed report/image retrieval features only.

## 6. Candidate-level feature schema

The feature schema is fixed before development implementation:

```text
text_score_normalized
image_score_normalized
text_rank_fraction
image_rank_fraction
text_image_score_difference
text_top1_margin
image_top1_margin
question_type_findings
question_type_impression
question_type_summary
```

The first seven features are candidate/retrieval-state features. The final
three are a one-hot question-type representation. No case ID, report text
hash, image filename, or target label is a feature.

## 7. Models and training objective

The primary learned scorer is a small feed-forward candidate scorer. A linear
scorer and a two-layer MLP comparator are both allowed during development:

```text
linear: 10 -> 1
MLP:    10 -> 32 -> 16 -> 1
```

Both use the same pairwise logistic ranking loss:

```text
softplus(-(score_positive - score_negative))
```

Positive candidates are the target report when it is present in the BM25
Top-100 shortlist. Target-outside-shortlist queries are excluded from pairwise
gradient optimization because they have no valid in-shortlist positive, but
remain in all retrieval evaluation metrics.

Negatives are selected deterministically from the same shortlist using the
highest-scoring non-target BM25 candidates and highest-scoring non-target
image candidates, with duplicate candidates removed. The negative count and
ordering are fixed in the implementation and recorded in the development
decision record.

The foundation encoders remain frozen. Optimizer, learning rate, weight decay,
epoch limit, early stopping, and model complexity are selected only on the
development data and then frozen before confirmation IDs are instantiated.

## 8. Development selection rules

Train A and Train B provide case-disjoint training folds. Validation is used
only for:

1. global-alpha grid selection;
2. linear-versus-MLP selection;
3. early-stopping checkpoint selection;
4. deterministic tie-breaking.

The global alpha grid is `{0.00, 0.01, ..., 1.00}`. The primary selection
metric is case-averaged MRR with equal weighting of the three question types.
If scores tie within the configured tolerance, choose the simpler model; for
global alpha ties choose the value closest to `0.50`, then the lower value.

The V8 confirmation cohort is never used for any of these decisions.

## 9. Primary and secondary hypotheses

Primary hypothesis H1:

> The frozen candidate-level reranker improves case-grouped MRR over the
> validation-selected global fusion comparator on the untouched V8 confirmation
> cohort.

H1 passes only when the lower bound of the prespecified 95% case-grouped
bootstrap confidence interval for reranker MRR minus global-fusion MRR is
greater than zero.

Secondary alignment hypothesis H2:

> The frozen reranker performs better with correctly aligned image features
> than under 100 deterministic fixed-point-free shuffled-image assignments.

For every shuffled assignment, all image-derived candidate features and the
reranker output must be recomputed. The plus-one Monte Carlo rule is
`(1 + exceedance count) / 101`, with a pass threshold of `p <= 0.05`.

## 10. QA transfer

After retrieval outcomes are frozen, reuse the unchanged MedGemma 1.5 prompt,
decoding, and V5/V6 verifier for a descriptive secondary QA transfer. Compare
BM25, validation-selected global fusion, and candidate-level reranker Top-1
reports. Report raw Token-F1, verified Token-F1, support rate, abstention rate,
revision rate, exact match, and source-balanced sensitivity.

QA outcomes cannot select the reranker or change H1/H2.

## 11. Claim boundary and stopping rule

If H1 passes, V8 may be described as evidence that candidate-level learned
reranking improved same-source paired-report retrieval under the frozen
protocol. If H1 fails, report the negative result and retain V7/V6 as the
principal evidence. A point estimate above the comparator without a positive
confidence interval is not a confirmed improvement.

No human evaluation, physician adjudication, clinical correctness, patient
independence, external validation, or deployment claim is made.

After the V8 technical freeze, no new model, feature, threshold, prompt,
dataset, or confirmation case may be added to this study.
