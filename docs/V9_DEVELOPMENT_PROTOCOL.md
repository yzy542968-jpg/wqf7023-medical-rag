# V9 Other-Patient Similar-Case Multimodal RAG: Development Protocol

## 1. Status and scope

This protocol defines a new development study after the V8 development no-go.
V5-V8 artifacts remain frozen. V9 confirmation case IDs are not generated by
this protocol.

The V9 task is:

> For a new patient without a report available to the system, use the chest
> radiograph, clinical indication, and medical question to retrieve clinically
> similar image-report cases from other patients, then generate an answer that
> separates target-image observations from historical supporting analogies.

The target findings and impression are hidden inference-time references. V9
is a retrospective technical evaluation, not autonomous diagnosis, clinical
deployment, or a medical-device study.

## 2. Research questions

RQ1: Does paired multimodal similar-case retrieval improve graded retrieval
quality over text-only and image-only retrieval?

RQ2: Does providing retrieved other-patient cases improve answer quality over
the same generator operating without retrieval?

RQ3: Is any multimodal gain dependent on the correctly aligned query image
rather than a text shortcut or generic image prior?

RQ4: Can a bounded evidence-control agent reduce unsupported claims without an
unacceptable loss in reference consistency?

## 3. Data roles and required fields

The final study requires a source with stable patient and study identifiers,
paired chest-radiograph images and reports, and report sections or equivalent
text. Preferred candidates are MIMIC-CXR or CheXpert Plus, subject to access,
license, local-compute, and contamination audits.

Each normalized record must contain:

```text
patient_id
study_id
image_paths
view_positions
indication
findings
impression
report_labels
radgraph_entities_relations
source_split
```

OpenI/IU-Xray may be used only for implementation smoke tests because reliable
patient identity is unavailable in the processed source. Such runs may verify
code behavior but cannot produce the primary V9 patient-disjoint claim.

## 4. Leakage-free partition and retrieval bank

All splits are patient-level when reliable patient IDs exist. The minimum
logical partition is:

```text
development/training patients
validation patients
untouched confirmation patients
```

For every query, the historical candidate bank must exclude:

1. the query study;
2. every study from the query patient;
3. every confirmation report when the fixed bank is defined as development
   patients only; and
4. any record failing the frozen readability and metadata checks.

The preferred confirmation design uses a fixed historical bank built only
from development patients. Validation and confirmation queries retrieve from
that same frozen bank. This prevents target reports from becoming candidate
evidence and makes leakage auditing straightforward.

No target findings, impression, report labels, RadGraph facts, answer, or
derived target-report embedding may be used by the inference pipeline. They
are evaluation-only fields.

## 5. Query, evidence, and output contract

The query input is:

```text
target chest radiograph view(s)
clinical indication/history available before reporting
medical question
```

The historical retrieval unit is:

```text
other-patient chest radiograph view(s)
paired findings and impression
study identifier for citation
```

The generator receives the target image, indication, question, and Top-k
retrieved report evidence. Historical images are used for retrieval and may be
displayed in the dashboard, but they are not required as generator pixel
inputs in the primary 8 GB GPU configuration.

The output schema is:

```json
{
  "answer": "...",
  "target_image_findings": ["..."],
  "supporting_case_ids": ["..."],
  "historical_support": "...",
  "uncertainty": "low|medium|high",
  "abstain": false
}
```

The prompt must state that historical cases are analogies, not proof that the
same finding exists in the target patient.

## 6. Question suite

The primary development suite uses fixed question forms that do not reveal the
target answer:

```text
findings:   What are the main radiographic findings?
impression: What is the most likely radiographic impression?
acute:      Is there an acute cardiopulmonary abnormality? Explain briefly.
```

A structured presence/location/negation suite informed by ReXVQA may be added
before the V9 confirmation protocol, provided its source, license, answer
construction, and text-only shortcut audit are recorded in the development
decision record. No case-specific question may be selected because it exposes
an answer from the hidden target report.

## 7. Operational clinical similarity

Because physician similarity judgments are unavailable, the primary retrieval
gold is explicitly named **report-derived graded relevance**. It is computed
offline from hidden target-report annotations and candidate-report annotations
and is never an inference feature.

Negative-label agreement receives no reward. Define an active-label weight as:

```text
positive  -> 1.0
uncertain -> 0.5
negative  -> 0.0
missing   -> 0.0
```

Label similarity is weighted Jaccard over active labels. If both reports have
no active abnormal label, label similarity is `1.0`; if only one has active
abnormal labels, it is `0.0`.

RadGraph similarity is the F1 overlap of normalized clinical entities and
relations. The primary continuous relevance gain is:

```text
gain(query, candidate)
  = 0.60 * active_label_similarity
  + 0.40 * radgraph_fact_similarity
```

The gain is constrained to `[0, 1]`. Binary Recall@K uses `gain >= 0.50` as the
prespecified relevant threshold. Sensitivity analyses report label-only and
RadGraph-only relevance without replacing the primary definition.

This operational relevance is not physician-adjudicated similarity.

## 8. Retrieval systems

All systems use the same candidate bank and deterministic case-ID tie rule.

```text
R0 Text-only:
   BM25(indication + question -> historical findings/impression)

R1 Image-only:
   MedSigLIP cosine(target image, historical image)

R2 Cross-modal image-report:
   MedSigLIP cosine(target image, historical report chunks)

R3 Fixed paired multimodal:
   validation-selected fusion of BM25, image-image, and image-report scores

R4 Learned paired reranker:
   small scorer over normalized scores, ranks, margins, and question type

R5 Shuffled-image control:
   R3/R4 recomputed after a fixed-point-free query-image permutation
```

BM25 parameters, MedSigLIP revision, image-view aggregation, report chunking,
score normalization, shortlist size, fusion grid, Top-k, and tie handling are
selected using development/validation data and frozen before confirmation.

The learned scorer may use pairwise loss weighted by the difference in graded
relevance. It must not receive case IDs, report text, filenames, target labels,
target facts, reference answers, or later QA outcomes as features. Foundation
encoders remain frozen.

## 9. Generation systems and prompts

The same frozen MedGemma revision, decoding parameters, and output parser are
used across generation conditions:

```text
G0 No retrieval:
   target image + indication + question

G1 Text RAG:
   G0 + R0 Top-k historical reports

G2 Fixed multimodal RAG:
   G0 + R3 Top-k historical reports

G3 Learned multimodal RAG:
   G0 + R4 Top-k historical reports, only if R4 passes development selection

G4 Agentic multimodal RAG:
   frozen selected retrieval + bounded route/check/retry/verify/abstain control
```

Prompt development is limited to a general prompt and an evidence-constrained
prompt. Selection occurs on validation only. The selected prompt and its
SHA-256 are frozen before confirmation. Confirmation answers cannot trigger
prompt edits.

## 10. Agent boundary

The primary retrieval and QA comparisons are fixed pipelines. The agentic
condition is a controlled secondary system layer with these states:

```text
INTAKE -> PLAN -> RETRIEVE -> ASSESS_EVIDENCE
       -> ANSWER -> VERIFY -> RETRY_OR_ABSTAIN -> COMPLETE
```

The controller may choose text-only, image-only, or paired retrieval from a
predefined rule set; perform at most one query rewrite/retrieval retry; remove
unsupported answer content; or abstain. It may not browse the internet, select
a new model, change thresholds, retrieve target-report fields, or perform an
unbounded loop.

Every action, query, retrieved study ID, score, verification decision,
latency, and reason is recorded in the trace.

## 11. Evaluation

Primary retrieval metric:

```text
patient-grouped nDCG@10 using continuous report-derived relevance gain
```

Secondary retrieval metrics:

```text
nDCG@5
Recall@1/5/10
MRR at gain >= 0.50
active-label coverage@k
target-study leakage count
target-patient leakage count
candidate-bank size
```

Primary structured QA metric is macro-F1 over prespecified report-derived
clinical labels when the selected dataset provides them. Open-ended QA reports
Token-F1, BERTScore, F1-CheXbert, and F1-RadGraph where dependencies and
licenses permit. Automated evidence support, abstention, revision, citation
coverage, unsupported-claim rate, latency, peak GPU memory, and retrieval-call
count are secondary outcomes.

All confidence intervals and paired comparisons are grouped by patient when
patient IDs exist. Question rows from one study are never treated as
independent patients.

## 12. Development selection and confirmation boundary

Development may select:

- fixed fusion weights;
- shortlist size and Top-k from a small prespecified grid;
- linear versus small-MLP learned scorer;
- early-stopping checkpoint;
- evidence-constrained prompt;
- one retry threshold and one abstention threshold.

The development decision record must report every candidate and negative
result. The confirmation protocol then freezes the selected source, source
revision, patient split, historical bank, qrels implementation, models,
prompts, thresholds, metrics, statistics, shuffled assignments, and failure
policy before final confirmation IDs are instantiated.

QA outcomes cannot select the retrieval model. Retrieval is selected only by
validation retrieval metrics. Agent outcomes cannot retroactively change the
fixed RAG baseline.

## 13. Planned hypotheses and advancement rules

The exact confirmatory hypotheses and margins will be frozen in the later V9
confirmation protocol. Development is organized around these candidate claims:

1. Fixed paired multimodal retrieval exceeds text-only retrieval on nDCG@10.
2. Correctly aligned paired retrieval exceeds the shuffled-image distribution.
3. The selected multimodal RAG condition exceeds no retrieval on the primary
   QA metric.
4. The agentic layer reduces unsupported claims without a prespecified
   material loss in the primary QA metric.

A learned reranker becomes the proposed primary retrieval method only if it
exceeds the validation-selected fixed multimodal comparator on validation
nDCG@10 under the prespecified simplicity tie rule. Otherwise the fixed fusion
remains primary and the learned result is reported as a no-go.

## 14. Claim boundary

Permitted claims are limited to retrospective technical performance,
report-reference consistency, report-derived clinical similarity, evidence
traceability, and alignment-specific image contribution under the frozen
study design.

The study does not establish physician-adjudicated diagnostic accuracy,
clinical safety, treatment recommendation quality, real-world utility, or
generalization beyond chest radiographs. Historical cases support comparison;
they are not direct evidence that a target finding is present.

## 15. Immediate development sequence

1. Commit this protocol and the related-work audit before code changes.
2. Add a synthetic paired-case schema, leakage auditor, qrels builder, and
   graded retrieval metrics with unit tests.
3. Adapt the existing OpenI data only for smoke tests and mark patient
   independence as unavailable.
4. Complete a dataset access and source-selection decision record.
5. Implement and validate R0-R3 before training R4.
6. Implement G0-G2 and the evidence-constrained output schema.
7. Extend the existing deterministic agent only after the fixed pipeline is
   stable.
8. Freeze the development decision record and a separate confirmation
   protocol before generating final confirmation IDs.
