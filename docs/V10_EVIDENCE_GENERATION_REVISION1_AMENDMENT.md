# V10 Evidence Generation Revision 1 Amendment

Status: frozen after the prompt-only JSON technical failure and before revised
Validation generation outcomes.

The failed attempt demonstrated that prompting MedGemma to emit nested JSON is
not a reliable control mechanism. Revision 1 adopts the prespecified V10
alternative of answer-first generation followed by deterministic schema and
provenance assembly.

## Revised execution

1. MedGemma receives the target image, indication, question, and selected
   historical evidence and generates only a concise plain-text answer.
2. Generation stops on the model's `<end_of_turn>` token or at 64 new tokens.
3. Python removes post-turn control text and normalizes the answer. A missing
   answer becomes the explicit inability statement already defined in the V10
   generation module.
4. Historical provenance is attached deterministically: from each retrieved
   case, the highest query-relevance evidence unit is retained when available,
   up to three units total. The exact selected unit text, provenance ID,
   `case_id`, section, and source hash are preserved. These are labelled
   `retrieved_historical_evidence`, not clinically adjudicated support.
5. Uncertainty is `high` when the answer contains an inability or insufficiency
   cue and `medium` otherwise. No low-uncertainty claim is generated by this
   deterministic layer.
6. Python assembles the final schema. No model-generated JSON is parsed or
   repaired, and no second generative support stage is used.

The three evidence policies, Validation frame, Token-F1 selection rule,
compactness tie rule, model revision, quantization, batch size, and Test
boundary remain unchanged. Engineering success is at least 99% complete
assembled rows. The failed 144-row attempt is excluded from policy comparison
and retained only as a technical-deviation artifact.
